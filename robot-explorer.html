The big picture: a robot is a really fast loop

Everything the robot does comes from one heartbeat. 50 times every second (every 20 milliseconds), the robot reads its sensors, runs its code, and commands its motors. This loop never stops — not while driving, not while scoring, not even while the robot is just sitting there disabled.

System 1 of 6

🛞 The Swerve Drivetrain

Most robots turn like a car. This one doesn't. Each of its four wheels can point in any direction while spinning — like shopping-cart wheels that you can also steer. That means the robot can drive sideways, diagonally, or pirouette without moving an inch.

top speed 4.0 m/s (~9 mph)
robot mass ~61 kg (135 lb!)
turn rate 0.5 rot/s
wheel steering gears 12.8:1
modules 4× MK4i

Swerve 101: three ideas before you drive

1 · Two motors per wheel

Each corner pod has a drive motor (spins the wheel) and a steering motor (rotates the whole pod), plus a CANcoder that reports the exact steer angle. One pod can point anywhere.

2 · One wish → four orders

The code says "go forward 3 m/s while spinning." Kinematics math converts that single wish into four (angle, speed) pairs — one order per wheel, 50 times every second.

3 · The wheels decide everything

Point all wheels forward → drive. Sideways → crab-walk. Fan them out → pirouette. Mix drive + spin → every wheel gets its own unique angle. Watch this happen live below.

The command that makes it all happen

The drive team's stick input arrives as a ChassisSpeeds — "go this fast forward, this fast sideways, spin this fast." The drive() function converts that single order into four separate wheel settings.

One order in, four wheels outsubsystems/drivetrain/DrivetrainSubsystem.java
public final void drive(ChassisSpeeds chassisSpeeds, boolean fieldRelative, boolean blueRelative, double... gain) {
    Rotation2d estimatedRotation = getEstimatedPose().getRotation();

    if (fieldRelative) {
        chassisSpeeds = ChassisSpeeds.fromFieldRelativeSpeeds(
            chassisSpeeds,
            blueRelative ? estimatedRotation : estimatedRotation.plus(Rotation2d.kPi)
        );
    }

    chassisSpeeds = ChassisSpeeds.discretize(chassisSpeeds, Robot.defaultPeriodSecs);
    SwerveModuleState[] desiredStates = m_kinematics.toSwerveModuleStates(chassisSpeeds);
    SwerveDriveKinematics.desaturateWheelSpeeds(desiredStates, 4.0);

    for (int i = 0; i < m_swerveModules.length; i++) {
        m_swerveModules[i].setDesiredState(desiredStates[i]);
    }
}
  • 1Field-relative math. The driver says "toward the hub," but the motors only understand "relative to the robot." This uses the gyro heading to translate. The kPi (180°) flip handles the red alliance, where the robot starts facing the other way.
  • 2Discretize — the loop only ticks every 20 ms, so the code converts a smooth continuous wish into "how far to actually move this one tick."
  • 3The kinematics magic. toSwerveModuleStates is a matrix calculation that solves: "to move + spin like this, each of the 4 wheels needs this angle and this speed." (It's the same math your swerve demo above is doing.)
  • 4Speed limit. If the math asks a wheel for 6 m/s but the motors top out at 4, clamp it — otherwise the wheel just spins at max and the robot's actual motion stops matching its math.
  • 5Finally, send every module its personal orders. 50 times a second. Forever.

Speed hack: the wheel flip

If turning would take more than 90°, the robot instead rotates the wheel the short way and drives BACKWARDS — a wheel rolling backwards at the flipped angle goes the same direction with a faster, smaller turn.
The 90° rule, in codesubsystems/drivetrain/swervemodule/SwerveModule.java
public final void setDesiredState(SwerveModuleState desiredState) {
    Rotation2d currentWheelAzimuth = getWheelAzimuthAsRotation();

    desiredState.optimize(currentWheelAzimuth);
    desiredState.cosineScale(currentWheelAzimuth);

    m_swerveModuleIO.setWheelVelocity(MetersPerSecond.of(desiredState.speedMetersPerSecond));
    m_swerveModuleIO.setWheelAzimuth(Radians.of(desiredState.angle.getRadians()));
}

public final boolean shouldOptimize(SwerveModuleState desiredState) {
    Rotation2d delta = desiredState.angle.minus(getWheelAzimuthAsRotation());
    return Math.abs(delta.getDegrees()) > 90.0;
}
  • 1optimize() is WPILib's built-in version of the trick you just played with: if the turn is >90°, flip the angle 180° and negate the speed.
  • 2cosineScale() handles an honest physics problem: a wheel pointed 60° off from where it wants to go only contributes cos(60°) = half its speed in the right direction. Scale the command so the effective speed stays correct.
  • 3This helper shows the raw rule: measure the difference between target and current wheel angle; if it's more than 90°, optimize. (One line of math can be a whole speed hack!)

How does the robot know where it is? Dead reckoning + a gyro

The wheels have encoders that measure how far they've rolled, and the Pigeon2 gyro measures every rotation of the robot. A pose estimator constantly fuses those signals — like navigating by counting your steps while a compass tells which way you turned. The camera system (see Vision) keeps it honest by occasionally saying "excuse me, you're actually here."

🧠 Pose = position + heading, written (x, y, θ). "Pose estimation" = combining noisy measurements from several sensors into the single best guess of where you are. It's the same family of math that powers your phone's location (GPS + wifi + motion sensors).

🎯 The Shooter: Flywheel · Turret · Hood · Kicker

Scoring means launching a foam "fuel" ball ~2 meters up into a spinning hub. The shooter is actually four mechanisms cooperating: a flywheel (the slingshot), a turret (rotates to aim left/right), a hood (tilts to set launch height angle), and a kicker (the pusher that feeds fuel into the spinning wheel at exactly the right moment).

The choreography as Javasubsystems/shooter/ShooterSubsystem.java
public final Command getShootCommand(IndexerSubsystem indexer) {
    return Commands.parallel(
        Commands.run(() -> {
            setFlywheelVelocity(RadiansPerSecond.of(SmartDashboard.getNumber("ShootingRPS", 460.0)));
        }, m_flywheel),

        Commands.repeatingSequence(
            Commands.waitSeconds(0.925),
            Commands.runOnce(() -> {
                indexer.setRunning(true, false, true);
                setKickerRunning(true, false);
            })
        ).finallyDo(() -> {
            setFlywheelVelocity(RadiansPerSecond.zero());
            setKickerRunning(false, false);
            indexer.setRunning(false, false, false);
        })
    );
}
  • 1Commands.parallel(...) means "run both of these at the same time." Commands are how FRC code describes activities with a start, a middle, and a stop.
  • 2Spin the flywheel to its target speed — and notice it reads the speed from the dashboard. Coaches can type a new RPM during a match without recompiling.
  • 3waitSeconds(0.925) — measured on the real robot: that's exactly how long the heavy flywheel needs to reach full speed. Physics has a speed limit (inertia!), so the code waits it out.
  • 4Only then does the kicker push fuel into the spinning wheel and the indexer feed more from behind.
  • 5finallyDo is a safety net: no matter how the command ends — driver lets go, robot disabled, emergency — everything stops. Clean shutdown, every time.

How steep should the shot be? (Real physics, solved live)

Fire a ball at 9.5 m/s at a hub that's ~1.3 m above the launcher, and there are exactly two launch angles that hit it — a flat, fast one and a high, lobbing one (try it with a basketball: same spot reachable at two arcs). The robot solves the projectile equation and picks the high arc, which drops fuel in from above like a basketball swish instead of a line drive that clangs off the rim.

🏹 Launch-angle solver SLIDE IT
Drag the distance slider. The code computes both possible angles and picks the higher one. Near the hub the shot is almost vertical (84°!); far away it flattens out (~63°). Push past max range to see the math break — the square root goes negative and there's simply no angle that reaches.

The quadratic formula shows up in real lifeutils/ShooterUtils.java
public static Pair<Angle, Angle> getQuadraticAngles(
    Distance horizontalDistance,
    Distance verticalDistance,
    LinearVelocity velocity
) {
    double v2 = Math.pow(velocity.in(MetersPerSecond), 2);
    double x = horizontalDistance.in(Meters);
    double y = verticalDistance.in(Meters);

    double principalRoot = Math.sqrt(Math.pow(v2, 2) - 9.8 * (9.8 * Math.pow(x, 2) + 2.0 * y * v2));
    double positiveRootAngle = Math.toDegrees(Math.atan((v2 + principalRoot) / (9.8 * x)));
    double negativeRootAngle = Math.toDegrees(Math.atan((v2 - principalRoot) / (9.8 * x)));

    return Pair.of(
        Degrees.of((positiveRootAngle < negativeRootAngle) ? positiveRootAngle : negativeRootAngle),
        Degrees.of((positiveRootAngle > negativeRootAngle) ? positiveRootAngle : negativeRootAngle)
    );
}
  • 1That's the discriminant from the quadratic formula — and that 9.8? Gravitational acceleration, m/s². Your physics class is literally running this robot. If the inside of the square root goes negative, no angle works (the shot is out of range).
  • 2+ principalRoot and - principalRoot = the two angles (high arc / low arc). atan converts the math ratio back into a real-world angle.
  • 3Returns both angles, sorted low then high. ShotCalculator then grabs .getSecond() — the high, swish-friendly arc.
System 3 of 6 · the brains

🧮 Auto-Aim: Leading a Moving Target

Here's a hard problem: by the time fuel reaches the hub (~0.4 s of flight), a moving robot will be somewhere else — and the shot was fired from where the robot used to be. The robot must aim where it will be, not where it is. Like throwing a ball to a friend while both of you are running.

There's no clean single formula for this (aim angle depends on distance, distance depends on lead, lead depends on flight time, flight time depends on angle…). So the code does something very computer-y: guess, check, improve, repeat — up to 10 times, stopping when the answer stops changing by more than 1 centimeter.

🎯 Watch the algorithm converge STEP THROUGH IT
The robot (bottom) moves with the arrow's velocity. The hub is up and to the right. Each iteration: measure distance to the current guess → physics gives hood angle + flight time → subtract robot's motion during that time → new guess. Press Step until the error falls below 1 cm.
Guess → check → improve. 50 times a second.subsystems/shooter/ShotCalculator.java
for (int i = 0; i < kMaxIterations; i++) {
    double distance = leadedOffset.getNorm();
    fuelVelocity = 9.5;

    hoodAngle = ShooterUtils.getQuadraticAngles(
        Meters.of(distance),
        Inches.of(71.5 - 21.5),
        MetersPerSecond.of(fuelVelocity)
    ).getSecond().in(Degrees);

    timeOfFlight = distance / (fuelVelocity * Math.cos(Math.toRadians(hoodAngle)));
    Translation2d nextLeadedOffset = targetTurretOffset.minus(inducedSpeeds.times(timeOfFlight));
    double delta = nextLeadedOffset.getDistance(leadedOffset);

    leadedOffset = nextLeadedOffset;

    if ((i >= (kMaxIterations - 1)) || (delta <= kSolutionTolerance.in(Meters))) {
        Logger.recordOutput("ShotCalculator/Iterations", i + 1);
        break;
    }
}
  • 1How far is the hub from my current guess? Fuel speed is a measured constant of the real robot.
  • 2Given that distance (and the hub being 50 inches above the launch point — 71.5 - 21.5), the projectile math spits back the hood angle for the high arc.
  • 3Horizontal speed × time = distance, so time = distance ÷ horizontal speed. Now we know how long the robot gets to wander during the shot.
  • 4The lead itself: shift the target backwards by however far the robot (and turret!) will travel during flight. Note inducedSpeeds cleverly includes the sideways speed from the robot rotating, since a turret mounted off-center swings through an arc.
  • 5If the answer barely moved (≤ 1 cm), we're done — usually in ~3 iterations. Otherwise loop again. This "iterate until it stops changing" trick is called fixed-point iteration, and it's how real engineering software solves impossible-looking equations.
🧠 Why not solve it exactly? Because the equation is circular — the variable you're solving for hides inside itself. Iteration is the honest way: a computer can check 3-10 candidates in a microsecond, and "accurate to 1 cm" is more precise than a 20 kg robot on a bumpy field ever needs.

Two more rules wrap the aiming: isShotPossible() geometry-checks the field map so the robot never tries to fire through the tower blocking part of the hub, and shouldStartShooting() checks the game's hub schedule so fuel isn't fired into a hub that's about to go inactive (wasted fuel = no points).

🌀 The Intake: Air-Powered Grabbing

The intake has two jobs: get down there and vacuum up fuel. Getting down there isn't done with a motor — it's done with compressed air. A piston punches the whole intake from tucked-up to deployed in a fraction of a second, faster and stronger than a motor could.

pneumatic piston + double solenoid (air valve)
roller motor 12.0 V (full send)
compressor keeps the tank at ~120 psi
💨 Pneumatics playground PRESS THE BUTTONS
B toggles the piston up/down (like on the controller). Hold LT to deploy + run the roller at once — that's the real "collect!" binding. Watch the air valve route air to either side of the piston.

public final void setRunning(boolean running) {
    if (running) {
        m_intakeIO.setIntakeMotorVoltage(Volts.of(12.0));
    } else {
        m_intakeIO.setIntakeMotorVoltage(Volts.zero());
    }
}

public final void toggleIntakeExtended() {
    m_intakeIO.setIntakeExtended(!m_intakeInputs.isIntakeSolenoidForward);
}
  • 1There's no fancy controller here — the intake's job is simple, so it gets all 12 volts, or zero. Good code isn't fancy code; it's enough code.
  • 2The toggle reads the solenoid's current state from the sensor inputs and flips it with ! (NOT). The piston doesn't have an "up" sensor position to home to — a valve is either switched one way or the other. Notice subsystems always read their own logged inputs rather than trusting a remembered boolean — sensors beat memory.
💨 How pneumatics work: a compressor stuffs air into a tank. A solenoid is an electrically-controlled valve — send current one way, air pushes the piston out; the other way, air pushes it back in. It's the same tech in excavators, dump-truck beds, and bus door openers. Fast, strong, and a very satisfying THWACK.
System 5 of 6

🚦 The Indexer: A Motorized Traffic Cop

Between the intake and the shooter sits a short storage tube with a small motor called the indexer. Its job: hold collected fuel in a neat train, and feed it into the shooter one ball at a time, exactly when asked. Too fast → jams. Too slow → the flywheel spins empty.

🐌 The indexer that slows itself down SLIDE THE HOOD ANGLE
Here's a gem from the real code: when the shot is steep (hood angle ≥ 75°, nearly straight up), the indexer ignores whatever speed it was asked for and runs at half voltage, because gravity already does most of the work feeding a vertical shot — pushing hard just packs fuel too fast and jams the shooter. Slide past 75° and watch it self-limit.

  • 1Yes, that's a real typo ("indexder") from the real source. Every programmer's code has these. Ship the robot anyway; fix it later.
  • 2It looks up the ShotCalculator's current launch angle and overrides slow itself. isFinite guards against "no valid shot computed yet" — garbage input can't crash the motor.
  • 33 volts forward, 1.5 volts when steep. Tiny numbers, because this motor just nudges fuel — the flywheel does the violent part.
  • 4Running reverse with positive voltage (while the shooter uses negative) — this motor's "forward" is wired to point fuel backward out of the robot, so spitting a jam means… running it forward. Wiring direction is a real, funny gotcha of hardware.
System 6 of 6

📷 Vision: Reading the Field's Barcodes

Dead reckoning (counting wheel turns) drifts — a small bump throws off every calculation after it. So the robot has three cameras scanning for AprilTags: square barcode-like stickers at known positions around the field. Spot one, and geometry tells you exactly where you are, like a lighthouse fix at sea.

cameras 3× (front-right, back-left, back-right)
single tags trusted only within 3.0 m
runs on PhotonVision coprocessors

But camera "fixes" can be wrong: a tag seen edge-on or far away gives a fuzzy position. The robot therefore doesn't just believe its cameras — it grades each measurement and only trusts it as much as it deserves. This grading function decides how much the pose estimator listens:

🤔 How much does the robot trust its camera? CHANGE THE SCENARIO
Zero tags → completely ignored. One tag far away → ignored (a distant barcode is too fuzzy). One nearby tag → listened to carefully, more if it appears large. Multiple tags → the best possible fix, and the size + count combine into the trust score. Adjust the sliders and see what the code concludes.
Grading the camera's homeworksubsystems/vision/VisionSubsystem.java
private static final Matrix<N3, N1> getPoseStdDevs(LoggableAprilTagDetection[] aprilTags) {
    double totalArea = 0.0;

    for (var aprilTag : aprilTags) {
        totalArea += aprilTag.area();
    }

    if (aprilTags.length <= 1) {
        if ((aprilTags.length == 0) || (aprilTags[0].distance() > kMaxSingleTagDistance.in(Meters))) {
            return kIgnoredStdDevs;
        } else {
            return kSingleTagStdDevs.div(totalArea);
        }
    }

    return kMultiTagStdDevs.div(totalArea / (1.0 + Math.log(aprilTags.length) / Math.log(2.0)));
}
  • 1Standard deviation ("std devs") = "how much wiggle-room I think this measurement has." Small = believe it. Huge = ignore it. The pose estimator weighs every sensor by its wiggle-room.
  • 2A tag that looks big in the camera is close, and close tags give sharper position fixes — so total visible area is a direct proxy for measurement quality.
  • 3No tags, or only one lonely tag farther than 3 m? Return "infinite uncertainty" — the vision measurement is politely thrown in the trash. Bad data in, bad driving out.
  • 4Multiple tags: divide by area and a logarithmic bonus for tag count (that log₂ — doubling the tags adds +1 bonus, with diminishing returns, just like real information theory).
🛰️ This "combine noisy sensors with confidence weights" idea is called sensor fusion — the same core idea in self-driving cars and the phone in your pocket. Your robot does it on a tiny computer, 50 times a second.
Under the hood

🏗️ One Brain, Three Bodies

Building a robot is risky — what if the code shorts a motor at 2 AM the night before a competition? This team's secret weapon: every line of robot code is written against fake hardware (an "IO interface"). Real motors, a video-game physics simulation, or a recorded match replay can all plug into the same brain.

  • 2Write motors: "spin at this rate" or "receive this voltage." The brain calls these verbs; three different bodies answer.

framework AdvantageKit (Team 254's open source)

Why log everything?

Every input — every motor velocity, every current spike, every shot computation — is written to a file during every run, tagged with the exact code version (git SHA) that produced it. After a match, engineers replay the robot's entire memory and scrub through the timeline like a DVR. When the flywheel was 30 RPM slow at 1:47… the log shows the battery sagging to 5 volts at 1:46.9. Debugging becomes detective work instead of guessing.

🧪 This whole pattern is called dependency injection (scary name, simple idea: you hand a machine the parts it needs instead of the machine grabbing them itself). You just used it on this page — the same demo brain ran on three different bodies. It's how professional software is built, and it made this team's season possible.
